# اتصال audit خارج از VPS به فضای ابری ParsPack

این راهنما برای profile تک‌سرور است. فضای ابری ParsPack از اتصال S3-compatible پشتیبانی
می‌کند؛ endpoint، Access Key و Secret Key از پنل گرفته می‌شوند. Secret Key مثل رمز عبور
است و نباید در chat، Git، command line، history یا log قرار بگیرد.

## قبل از شروع

1. در پنل پارس‌پک وارد «فضای ابری» و سپس «مدیریت دسترسی و کاربرها» شوید.
   کاربری را که کلید آن در chat فرستاده شده انتخاب کنید. با «تغییر رمزعبور» credential
   تازه ایجاد کنید و لغو credential قبلی را بررسی کنید. اگر کاربر مورد استفاده سامانه
   دیگری است، آن اتصال را هم با کلید تازه به‌روز کنید. کلید تازه را در chat نفرستید.
2. با «افزودن کاربر جدید» یک کاربر جداگانه برای audit بسازید. به آن «دسترسی کامل» ندهید.
   در «مدیریت دسترسی»، گزینه «سفارشی» را بررسی کنید. حساب ارسال‌کننده نباید اجازه حذف
   یا بازنویسی audit یا مدیریت retention داشته باشد؛ اگر پنل چنین محدودیتی ندارد، `off-host audit integrity`
   تا زمان فراهم‌شدن کنترل retention/عدم‌حذف `Not verified` می‌ماند.
3. باکت audit را خصوصی نگه دارید. عمومی‌بودن باکت، فایل‌های امنیتی را در اختیار دیگران
   می‌گذارد. یک bucket یا prefix جدا برای audit در نظر بگیرید؛ مقصد نهایی و ظرفیت پس از
   اندازه‌گیری حجم تعیین می‌شود. قبل از تنظیم retention، پشتیبانی آن را تأیید کنید.
   فولدر دیگر روی همین VPS یا IP دوم، مقصد مستقل محسوب نمی‌شود.

## این سؤال را برای پشتیبانی پارس‌پک بفرستید

«برای همین باکت آیا Object Lock با retention اجباری، یا حالت append-only واقعی دارید؟
آیا می‌توان به حساب ارسال فقط ایجاد آبجکت جدید داد و حذف، بازنویسی آبجکت قبلی و تغییر
retention را از آن گرفت؟ اگر حساب ارسال روی VPS افشا شود، آیا audit قبلی باز هم محفوظ
می‌ماند؟ گزینهٔ «حالت قفل» پنل دقیقاً چه قابلیتی است، آیا retention اجباری و
غیرقابل‌کاهش دارد، و فعال‌کردن آن برگشت‌پذیر است؟ لطفاً روش تنظیم و محدودیت‌های
آن را اعلام کنید.»

راهنماهای عمومی بررسی‌شده روش اتصال، کاربران سفارشی و خصوصی/عمومی‌بودن باکت را توضیح
می‌دهند؛ اثباتی برای Object Lock، retention اجباری یا منع overwrite این باکت نیستند.
پاسخ پشتیبانی به‌تنهایی هم آزمون واقعی را جایگزین نمی‌کند. اگر این امکانات وجود نداشته
باشد، این فضا می‌تواند مقصد backup باشد، اما به‌تنهایی مقصد audit مصوب محسوب نمی‌شود.

## تحویل امن تنظیمات

### ادامهٔ اجرایی ۱ اکتبر ۲۰۲۶

مالک کلیدهای تازه را در فایل خصوصی و Git-ignored
`.platform-runtime/production/private/parspack-audit-credentials.json` قرار داد و
مقصد جدید `https://c892683.parspack.net` را تعیین کرد. فایل `0600` و پوشهٔ
private برابر `0700` است. آزمون GET امضاشده روی مسیر `/c892683`، برای
Object Lock پاسخ `HTTP 403; AccessDenied` و برای Versioning پاسخ
`HTTP 200; Versioning not configured` داد. این وضعیت متعلق به باکت جدید است؛
تأیید قبلی مالک برای Compliance/۴۰ روزِ `c426797` به این مقصد منتقل نمی‌شود.
مالک سپس فعال‌سازی نسخه‌سازی و Compliance/۴۰ روز را برای مقصد جدید اعلام کرد.
آزمون مجدد همان GETها هنوز همان پاسخ‌ها را داد. این اعلام مالک ثبت می‌شود، اما
پاسخ API دربارهٔ تنظیمات جدید همچنان `Inconclusive` است.
یک آبجکت مصنوعی ۱۱۳ بایتی با کلید یکتای
`hooshix-audit-preflight/50a83b66-5d9e-49f7-a42a-921f012fab94.json`
ایجاد شد: PUT و GET برابر `HTTP 200` و هش محتوای خوانده‌شده برابر بود؛ اتصال
امضاشده و round-trip مصنوعی `Passed` است. پاسخ PUT/GET هیچ `x-amz-version-id`
غیر-null نداشت و GET retention همین آبجکت `403; AccessDenied` داد.
DELETE بدون versionId روی همین آبجکت ساخته‌شده `204` داد و GET بعدی `404` شد؛
این فقط حذف از نمای عادی و مجوز حذف بدون versionId را نشان می‌دهد، نه حذف نسخهٔ
قفل‌شده یا اثبات نبود retention. آبجکت از نمای عادی پاک شد؛ بازیابی نسخهٔ احتمالی
`Not verified` است. آبجکت دیگری لمس نشد و دادهٔ واقعی کاربر ارسال نشد.
تنظیمات باکت/VPS تغییر نکرد و credential به VPS یا CI منتقل نشد.
تا اثبات نسخه‌سازی و حفاظت مقصد جدید، ممیزی خارجی و grant واقعی JIT
`Not verified` باقی می‌مانند. تغییرات ابزار بررسی و تست‌های آن در یک PR واحد
ادامه می‌یابد؛ وضعیت SSH/پورت MCP خارج از این تغییر است.

### اجرای امن ابزار با فایل خصوصی

ابزار اکنون می‌تواند ورودی محلی JSON را بدون prompt از همان فایل بخواند. فایل باید
متعلق به کاربر اجراکننده، regular، بدون symlink/hardlink، با دسترسی دقیق `0600` و
پوشهٔ والد متعلق به همان کاربر با دسترسی `0700` باشد. ورودی بیش از ۸ KiB، JSON
نامعتبر/فیلد تکراری، secret خالی یا دارای control character و مقصد مغایر رد می‌شوند.
فیلدهای ضروری `access_key` و `secret_key` هستند؛ یک فیلد اختیاری endpoint با نام
`endpoint`، `endpoint_url` یا `end_point_url` پذیرفته می‌شود. مقدار آن باید با
endpoint صریح فرمان یکسان باشد؛ نشانی بدون scheme به HTTPS تبدیل می‌شود.
مقادیر واقعی فقط در فایل private می‌مانند؛ نمونهٔ credential در Git لازم نیست.

```bash
python3 scripts/production/probe_parspack_audit_bucket.py \
  --endpoint https://c892683.parspack.net --bucket c892683 \
  --credentials-file .platform-runtime/production/private/parspack-audit-credentials.json \
  --require-compliance-days 40
```

فرمان فقط دو GET می‌فرستد؛ مقدار secret در argv، environment یا خروجی چاپ نمی‌شود.
`--require-compliance-days 40` تنها برای تنظیمات قابل‌خواندن و دقیق
`COMPLIANCE / 40 days` همراه Versioning Enabled، exit code صفر می‌دهد؛ در صورت
قطع ارتباط، 403، پاسخ HTML، Governance یا مدت متفاوت exit code یک برمی‌گردد.
exit code صفر فقط `READ_ONLY_CONFIGURATION=Passed` است و ابزار صریحاً audit readiness
و منع حذف/بازنویسی را تأیید نمی‌کند. این ورودی private صرفاً ورودی operator برای
preflight است؛ provision/receiver نیست و جایگزین OpenBao در Production نمی‌شود.
این مسیر نباید با کلید واقعی روی runnerهای GitHub اجرا شود. تست‌های ساختگی آن از
همان `make production-verify` در pipeline موجود Repository baseline اجرا می‌شوند.

قدم رفع مانع مقصد جدید: نام باکت/تنظیمات در پنل با مسیر `/c892683` تطبیق داده شود؛
حساب writer فقط ایجاد/خواندن لازم داشته باشد و مجوز DELETE و تغییر retention نداشته
باشد. خواندن تنظیمات versioning/Object Lock و retention برای preflight باید مجاز
باشد یا evidence مستقل از حساب بررسی‌کنندهٔ جداگانه فراهم شود. حساب writer را
برای دورزدن 403 به مالک/full-access تبدیل نکنید. تا نسخهٔ قابل‌شناسایی، retention
قابل‌اثبات و آزمون نسخهٔ مشخص فراهم نشده، ارسال ممیزی عملیاتی و JIT نصب/فعال نشوند.

نام endpoint و باکت اطلاعات اتصال هستند؛ Access Key و Secret Key باید در پنجره محلی
محافظت‌شده وارد شوند. ابزار provision نهایی باید مقدارها را بدون echo و بدون argv،
history، environment عمومی یا log دریافت کند و از مسیر bootstrap مصوب به OpenBao
منتقل کند. کاربر نباید secret را داخل سورس یا فایل sample بنویسد. در این نسخه ابزار
provision و receiver هنوز نصب نشده‌اند؛ این بخش دستور اجرای ابزار موجود نیست.

## بررسی فقط‌خواندنی باکت فعلی

مالک، endpoint و نام باکت `c426797.parspack.net` / `c426797` را اعلام کرده است.
پاسخ بدون احراز هویت به یک کلید ناموجود، نام باکت `c426797` را نشان داد؛ این فقط
تطابق نشانی با باکت است، نه اثبات اتصال احراز هویت‌شده. برای بررسی Object Lock و
Versioning، مالک می‌تواند در ترمینال شخصی WSL، از checkout بازبینی‌شده اجرا کند:

```bash
python3 scripts/production/probe_parspack_audit_bucket.py \
  --endpoint https://c426797.parspack.net --bucket c426797
```

در ۳۰ سپتامبر ۲۰۲۶ آزمون اولیهٔ ریشهٔ endpoint برای هر دو query پاسخ HTML عمومی
`HTTP 200` داد؛ این اتصال S3 مدیریتی را ثابت نمی‌کند. پروفایل رسمی Cyberduck
پارس‌پک `s3-path-style` و غیرفعال‌بودن virtual-host را مشخص می‌کند؛ بنابراین نسخهٔ
اصلاح‌شده، درخواست‌ها را به مسیر `/<bucket>?...` می‌فرستد. ابزار باید در ترمینال
WSL/Linux اجرا شود، نه از PowerShell روی مسیر UNC مخزن.

اجرای اصلاح‌شده توسط مالک در WSL برای همین باکت، `Versioning: HTTP 200; Enabled`
و `Object Lock: HTTP 403; AccessDenied` برگرداند. این پاسخ اول اتصال امضاشده و
فعال‌بودن versioning را نشان می‌دهد؛ پاسخ دوم دربارهٔ فعال‌بودن Object Lock
نامعین است، زیرا ممکن است مجوز خواندن تنظیمات وجود نداشته باشد. Versioning به‌تنهایی
مانع ایجاد delete marker یا حذف نسخه توسط صاحب مجوز نمی‌شود. بنابراین وضعیت
`off-host audit integrity` همچنان `Not verified` است و تا مشاهدهٔ تنظیمات مجاز
و اجرای آزمون عدم‌حذف/عدم‌بازنویسی نباید به‌عنوان gate JIT استفاده شود.
مالک ابتدا وضعیت پنل را چنین اعلام کرد: باکت خصوصی، نسخه‌سازی فعال، «حالت قفل»
غیرفعال و وب‌سایت استاتیک فعال. سپس در ۳۰ سپتامبر ۲۰۲۶ اعلام کرد که قابلیت قفل
را از پارس‌پک پرسیده و فعال‌بودن آن را تأیید گرفته، فعال‌سازی قفل را مجاز می‌داند،
و پنل اکنون حالت `Compliance` با نگهداری ۴۰ روزه را نشان می‌دهد. اینها گزارش و
تأیید مالک هستند. پاسخ API پیشین `HTTP 403; AccessDenied` مربوط به قبل از این
گزارش بود. مالک پس از اجرای مجدد ابزار فقط‌خواندنی در WSL تأیید کرد که خروجی
کامل `HTTP 200; Object Lock enabled; default retention COMPLIANCE / 40 days`
و `HTTP 200; Versioning Enabled` را می‌بیند؛ خروجی خام/receipt مستقل نزد عامل
ثبت نشده و آزمون رفتاری هنوز انجام نشده است. بنابراین پیکربندی قفل به گواه
مالک و API خواندنی **Partially verified** است، اما `off-host audit integrity`
همچنان `Not verified` می‌ماند. معنی دقیق و ضمانت عدم‌حذف پارس‌پک در منابع عمومی
آن یافت نشد؛ اثر قفل بر آبجکت‌های جدید و قبلی، مجوزهای حساب نویسنده و عدم‌حذف/
عدم‌دستکاری نسخه‌های آزمایشی در دورهٔ نگهداری باید با شواهد مستقل بررسی شوند.

ابزار، دو کلید را بی‌صدا می‌پرسد و فقط درخواست‌های GET امضاشده می‌فرستد؛ آنها را
در chat، argv، environment، تاریخچه shell یا فایل ذخیره نمی‌کند. خروجی متنی آن
را می‌توان بدون کلید به مسئول بررسی داد. `HTTP 403` ممکن است نبود مجوز خواندن
تنظیمات را نشان دهد و اثبات نبود Object Lock نیست. `HTTP 200` همراه با
`Object Lock enabled` و default retention هم هنوز مجوز حذف/بازنویسی حساب ارسال‌کننده
یا integrity واقعی را اثبات نمی‌کند؛ آزمون منفی روی آبجکت آزمایشی و نگهداری receipt
خارج از VPS همچنان لازم است. این ابزار provision یا receiver نیست و هیچ credentialی
را به OpenBao منتقل نمی‌کند.

## رفتار لازم

- batch audit باید شناسه یکتا، ترتیب و integrity قابل بررسی داشته باشد؛ hash به‌تنهایی
  جلوی حذف یا بازنویسی به‌دست حساب دارای write را نمی‌گیرد.
- فایل‌های ارسالی باید خارج از اختیار نویسنده، append-only یا دارای retention/object
  lock باشند. اگر ParsPack برای bucket انتخاب‌شده این کنترل را ارائه نکند، ارسال از
  طریق TLS به‌تنهایی شرط audit مصوب را برآورده نمی‌کند.
- آزمون عدم‌حذف باید نسخهٔ مشخص یک آبجکت آزمایشی را هدف بگیرد و باقی‌ماندن همان
  نسخه و هش محتوایش را بررسی کند. در رفتار مرجع S3، حذف بدون `versionId` حتی با
  Object Lock می‌تواند delete marker بسازد و آبجکت را از نمای عادی پنهان کند؛
  ایجاد نسخهٔ جدید با همان کلید نیز نسخهٔ قفل‌شدهٔ قبلی را از بین نمی‌برد. بنابراین
  دریافت‌کننده باید شناسهٔ نسخه و receipt مستقل نگه دارد و حساب نویسنده حق حذف،
  بازنویسی کلیدهای audit یا تغییر retention نداشته باشد. این رفتار برای پارس‌پک
  هنوز با آزمون واقعی تأیید نشده است.
- قطع endpoint، خطای TLS، خطای احراز هویت یا پرشدن صف باید grant جدید JIT را fail-closed
  کند. پردازش عادی برنامه نباید به audit معمولی وابسته شود.
- بعد از برقراری ارتباط، دریافت واقعی، قطع مقصد، پرشدن صف، برگشت ارتباط، تغییر hash و
  تلاش حذف/بازنویسی را با receipt بدون secret تست کنید.

## چیزی که این راهنما ثابت نمی‌کند

وجود endpoint یا فایل config به‌تنهایی evidence تولید نیست. تا وقتی credential تازه،
bucket policy، receiver، retention و تست‌های مثبت/منفی روی VPS اجرا و receipt آن خارج از
میزبان نگهداری نشده، وضعیت audit خارجی `Not verified` است.
