# دسترسی امن مدیریت Production — راهنمای ساده

## WireGuard، peer و JIT یعنی چه؟

- WireGuard یک مسیر خصوصی بین کامپیوتر مدیر و سرور است.
- peer یعنی یک دستگاه ثبت‌شده در همین مسیر؛ برای هر دستگاه کلید مستقل وجود دارد.
- کلید SSH جداگانه تعیین می‌کند چه کسی حق ورود دارد. داشتن WireGuard به‌تنهایی ورود نمی‌دهد.
- JIT یعنی اجازه مدیریتی فقط برای کار مشخص و زمان کوتاه، حداکثر ۳۰ دقیقه، صادر و سپس خودکار لغو شود.
- audit یعنی ثبت قابل بررسی کارهای مدیریتی؛ تاریخچه shell یا backup هفتگی جای آن را نمی‌گیرد.

## روش انتخاب‌شده

برای profile تک‌سرور، FIDO2 اختیاری است. خرید یا ارائه آن شرط استقرار نیست.
روش بدون سخت‌افزار، کلید مستقل Ed25519 رمزدار با مجوز فایل محدود است.
این روش مثل FIDO2 کلید غیرقابل استخراج و تأیید حضور سخت‌افزاری ندارد. رمزگذاری فایل کلید
را نمی‌توان از تنظیمات سمت سرور تضمین کرد؛ در زمان enrollment روی دستگاه مالک بررسی می‌شود.
MFA کاربران اپلیکیشن و سیاست profile HA تغییری نمی‌کنند.

## اتصال موجود را دوباره نسازید

در بررسی ۲۷ سپتامبر ۲۰۲۶، دستگاه Windows فعلی از تونل hooshix-server با آدرس
10.77.47.2/32 به management سرور 10.77.47.1/32 می‌رود؛ مسیر مجاز فقط همین آدرس است.
Endpoint عمومی WireGuard برابر 188.240.196.151:51820 است. alias SSH فعلی از
پورت موقت 22022 و حساب hooshixadmin استفاده می‌کند. این اطلاعات شواهد go-live نیستند.
peer سمت سرور باید با public-key fingerprint همان دستگاه تطبیق داده شود.
private key یا فایل کامل config را در chat یا Git نفرستید.

## کارهای اجرایی مدیر نصب

1. peer موجود و fingerprint عمومی دستگاه را پیدا و با وضعیت سرور تطبیق دهید؛ کلید فعلی را بازتولید نکنید.
2. مالک، دستگاه، آدرس مجاز، fingerprint، زمان ثبت و روش revoke را در inventory محافظت‌شده ثبت کنید.
3. کلید SSH مستقل، حساب نام‌دار و مجوز فایل و رمز کلید را بررسی کنید.
4. قبل از تغییر، تمام SSH listenerها، socket activation، تنظیمات مؤثر و firewall را بررسی کنید.
   مسدودکردن فقط TCP/22 کافی نیست؛ پورت‌های SSH دیگر مثل 22022 و 2222 نیز باید بررسی شوند.
5. یک نشست فعال و نشست دوم برای تست مسیر مدیریت و rollback زمان‌دار نگه دارید.
   sshd -t و sshd -T اتصال‌محور باید قبل از reload و پس از آن بررسی شوند.
6. SSH فقط از آدرس/interface management قابل ورود باشد؛ مسیر عمومی و forwarding غیرضروری بسته باشد.
   در policy این repository، `DisableForwarding yes` و `AllowStreamLocalForwarding no`
   علاوه بر Agent/TCP/X11/tunnel denial وجود دارند. global output به‌تنهایی کافی نیست؛
   تنظیم مؤثر هر حساب و `Match` را جداگانه بررسی کنید. وجود این فایل در Git به معنی اعمال روی VPS نیست.
7. ورود بدون کلید، root، password، کلید ناشناس و peer ناشناس باید رد شوند.
   تست revoke را با peer آزمایشی مستقل انجام دهید؛ peer تنها مسیر مدیریت را حذف نکنید.
8. JIT با دلیل/ticket، یک تأییدکننده نام‌دار و انقضای خودکار پیاده‌سازی و تست شود. این انتخاب فقط برای تک‌سرور است و به‌دلیل نبود نفر دوم، ریسک تفکیک وظایف را صریحاً می‌پذیرد.
   تغییر دائمی sudoers یا ذخیره رمز sudo در automation جایگزین آن نیست.
   حذف sudoers یا پایان اعتبار SSH certificate به‌تنهایی آزمون پایان privilege فعال نیست.
   آزمون expiry باید شامل نشست فعال، processهای child/background، grant تکراری، reboot،
   تغییر ساعت و قطع audit باشد. بدون کنترل فعال این مسیرها، JIT را Passed اعلام نکنید.
9. audit OS، SSH، sudo I/O، Kubernetes و database را در مسیرهای محافظت‌شده ثبت کنید.
   ورودی command و session ممکن است secret داشته باشد؛ رمز/token را در command یا session ضبط‌شده وارد نکنید.
10. audit به مقصد TLS-authenticated خارج از VPS با نگهداری مقاوم به دستکاری صادر شود.
    قبل از claim، دریافت واقعی، قطع مقصد، ظرفیت صف، برگشت ارتباط و integrity را تست کنید.
    قطع audit باید صدور elevation جدید را متوقف کند؛ نباید سرویس عادی یا مسیر بازیابی را از کار بیندازد.

## فقط چه ورودی‌هایی از مالک لازم است؟

- احراز هویت sudo در پنجره محلی برای اجرای بررسی و تغییر مصوب؛ رمز در chat یا فایل قرار نمی‌گیرد.
- مقصد واقعی audit خارج از این VPS با مشخصات عمومی endpoint/TLS/retention و حساب نویسنده محدود؛
  credential از مسیر خصوصی مصوب provision شود.
- هویت یک مسئول مجاز برای approval JIT؛ در تک‌سرور همان یک نفر می‌تواند درخواست را بررسی و تأیید کند، اما هویت، دلیل/ticket، scope و زمان انقضا باید مستقل و قابل حسابرسی ثبت شود.

این ورودی‌ها را نمی‌توان از روی سورس ساختگی اعلام کرد.
اگر FIDO2 استفاده نشده، تست‌های مختص آن Not applicable هستند؛ تست SSH/JIT/audit حذف نمی‌شود.

## آماده‌سازی مقصد audit بدون نیاز به دانستن تنظیمات فنی

اگر مقصد دیگری ندارید، باید دسترسی به یک میزبان مستقل یا سرویس نگهداری audit خارج از
این VPS فراهم شود. IP دوم همین VPS، فولدر دیگر همان VPS، backup هفتگی و Loki روی همان
سرور این استقلال را ایجاد نمی‌کنند. انتخاب ظرفیت و retention بعد از اندازه‌گیری حجم
audit انجام می‌شود؛ خرید سرویس یا واردکردن credential بدون تصمیم مالک انجام نمی‌شود.

مالک فقط دسترسی امن به مقصد را فراهم می‌کند؛ نصب receiver، TLS، حساب ارسال محدود،
سیاست retention، منع حذف/بازنویسی توسط حساب ارسال‌کننده و تست دریافت/قطع/بازیابی
باید توسط مدیر نصب انجام شود. endpoint به‌تنهایی کافی نیست؛ دریافت واقعی و کنترل
دسترسی مقصد باید evidence داشته باشند. credential را در chat نفرستید.

## آماده‌سازی approval واقعی JIT

برای profile تک‌سرور، طبق تصمیم مالک در ADR-0030، حداقل یک reviewer نام‌دار کافی است.
همان مدیر می‌تواند درخواست‌کننده و تأییدکننده باشد؛ لازم نیست نفر دوم بسازید یا معرفی
کنید. چند نام یا کلید برای یک شخص، چند تأییدکننده مستقل ایجاد نمی‌کند. تأییدکننده دوم
در تک‌سرور مجاز ولی اجباری نیست. profile HA همچنان دو reviewer مستقل و MFA سخت‌افزاری می‌خواهد.

## JIT در استفاده روزمره چگونه خواهد بود؟

این مراحل رفتار لازم ابزار نهایی را توضیح می‌دهند؛ در نسخه فعلی ابزار اجرایی JIT نصب
نشده است و نباید این راهنما را به‌عنوان راه‌اندازی‌شدن آن برداشت کنید.

1. ابتدا WireGuard را وصل می‌کنید و با کلید SSH شخصی وارد مسیر مدیریت می‌شوید. ورود
   به‌تنهایی اجازه تغییر Production نمی‌دهد.
2. کار موردنظر و دلیل آن را انتخاب می‌کنید؛ مثلاً «بررسی خرابی یک سرویس» با شماره
   پیگیری. scope باید فقط همان کار را پوشش دهد، نه دسترسی دائمی یا نامحدود.
3. زمان کوتاه لازم را مشخص می‌کنید؛ برای نوشتن حداکثر ۳۰ دقیقه. زمان بیشتر، درخواست
   بدون دلیل/پیگیری و approval بدون هویت معتبر باید رد شود.
4. به‌عنوان همان مدیر مجاز، درخواست را با هویت خود تأیید می‌کنید. automation نمی‌تواند
   approval شما را جعل کند یا صرفاً با نوشتن عدد «۱» مجوز بسازد.
5. قبل از grant، دریافت audit خارج از VPS و سلامت مسیر ثبت باید تأیید شود. قطع audit
   یا نبود evidence معتبر، صدور مجوز جدید را مسدود می‌کند.
6. مجوز دقیق فقط تا deadline کار می‌کند. پایان اعتبار باید privilege نشست و processهای
   فعال را هم کنترل کند؛ پاک‌کردن یک فایل sudoers کافی نیست.
7. نتیجه، شناسه grant، هویت مدیر، scope، زمان شروع/پایان و revoke ثبت می‌شود؛ secret
   یا محتوای خصوصی کاربران در receipt قرار نمی‌گیرد.

نصب‌کننده باید enrollment، ابزار grant/revoke/expiry، audit و تست‌های این مراحل را
انجام دهد. از مالک فقط ورود امن اطلاعات حساب و احراز هویت محلی خواسته می‌شود؛ نصب
فنی یا نوشتن دستورات امنیتی به مالک واگذار نمی‌شود.

## وضعیت اجرای این بخش

این راهنما و policyها، اجرای JIT یا off-host audit را ثابت نمی‌کنند. برای مقصد ParsPack
راهنمای provision امن در `production-audit-sink-parspack-fa.md` قرار دارد؛ credential افشاشده
باید قبل از هر استفاده rotate شود. تا وجود receiver
واقعی، provision هویت‌ها، کنترل expiry و اجرای آزمون‌های منفی، هر دو کنترل
`Not verified` هستند. نصب/تغییر privileged روی host همچنین به احراز هویت sudo
در پنجره محلی نیاز دارد؛ رمز ذخیره، در Git ثبت یا از chat بازاستفاده نمی‌شود.
