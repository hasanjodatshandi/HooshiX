# ADR-0054: Harden Semantic-Quota Time Safety v1

## Status

Accepted

## Date

2026-08-11

## Supersedes

This ADR supersedes ADR-0041 only where quota refill treated Redis server wall
clock as the sole time authority and where Redis key TTL could implicitly reset
a security budget.

All ADR-0041 ownership, atomicity, pseudonymization, anti-lockout, quota
coverage, capacity/cost policy, Redis topology, failure semantics, and
production verification requirements remain accepted unless explicitly changed
here.

## Context

A centralized Redis clock avoids disagreement between application replicas, but
wall-clock manipulation or a large NTP step on the Redis host must not create
fresh quota credit. Redis expiry is also based on wall time, so `PTTL` is useful
for observability/cleanup but is not an independent security time source.

The limiter therefore needs clock-diversity and fail-closed behavior without
turning client-supplied time into an input to authorization decisions.

## Decision

### Trusted dual-clock input

Each limiter invocation supplies an `app_wall_time_ms` generated by the
application process immediately before the Redis call. It is never accepted
from HTTP, gRPC, browser, Kafka, or other caller-controlled input.

The single reviewed Redis Function/Lua operation also reads Redis `TIME`.

The two values are validated before refill:

```text
max allowed absolute app/Redis skew = 2 seconds
```

If the absolute difference exceeds the bound, the limiter fails closed with:

```text
UNAVAILABLE / QUOTA_TIME_SOURCE_UNHEALTHY
```

No quota token is granted or consumed from a partially evaluated decision.

### Effective refill time

For a valid sample:

```text
effective_now = min(redis_time, trusted_app_time)
```

Each bucket stores its last accepted `effective_now`. Stored effective time is
monotonic: a backward step provides zero refill and never moves bucket time
backward.

Using the minimum prevents a forward jump in only one clock from creating
premature refill credit. A valid long idle period can still refill only up to
the configured bucket capacity.

### Expiry is not security authority

Security-critical quota state MUST NOT rely on Redis key expiry to decide that
a budget has reset. A Redis wall-clock jump therefore cannot reset a quota by
expiring the authoritative bucket key.

Quota records retain their decaying/refilling state without a security-significant
TTL. A bounded janitor performs non-authoritative cleanup only when:

- the bucket has mathematically returned to full capacity or zero failure pressure;
- the stored last-use time is older than the operation's cleanup horizon;
- current application and Redis clocks pass the same skew validation; and
- deletion is performed in bounded batches.

If the janitor is unavailable or time health is uncertain, state is retained.
Memory growth alerts before `noeviction` capacity is endangered.

`TTL`/`PTTL` may be used for non-authoritative telemetry or auxiliary keys, but
never as the sole reason to grant fresh security capacity.

### Clock hardening and observability

Redis and application nodes use the production time-synchronization baseline.
Metrics expose bounded clock-skew buckets and time-source unhealthy counts; raw
IP addresses, user/tenant identifiers, or quota pseudonyms are not metric
labels.

No application may bypass a failed time-safety decision with a local fallback.

## Verification Requirements

Tests must cover:

- Redis clock forward jump;
- Redis clock backward jump;
- application clock forward/backward jump;
- skew exactly at and beyond the two-second boundary;
- no refill when one source jumps forward;
- no security reset caused by key expiry;
- janitor safety under clock mismatch;
- long-idle refill capped at configured capacity;
- atomic multi-dimension behavior and no partial consumption;
- Redis failover while retaining quota state;
- memory-growth alerts and bounded cleanup;
- PII-safe telemetry.

## Consequences

- Compromise or severe drift of one clock cannot silently refill a bucket.
- Quota availability now depends on agreement between two infrastructure clocks,
  which intentionally fails closed for sensitive operations.
- Security state may live longer in Redis than its previous TTL; bounded cleanup
  and memory monitoring become mandatory.
- `PTTL` remains useful operationally but is not treated as a separate trusted
  clock.

## Rollback Considerations

Rollback must not restore sole Redis-wall-clock refill or security-significant
key expiry. A rollback that cannot enforce the dual-clock contract must disable
the affected production semantic-quota entry points.
